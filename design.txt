MMIO モデル
===========

Wasmの WebAssembly.Memory（ArrayBuffer）内の特定の固定アドレス領域を
「I/Oレジスタ」および「DMAリングバッファ」として定義します。

+-------------------------------------------------------------+
|                  WebAssembly.Memory                         |
|                                                             |
|  [0x0000 - 0x7FFF] User Code / Heap / Stack                 |
|                                                             |
|  [0x8000 - 0x80FF] MMIO Control Registers (128 - 256 B)     |
|      - Status Flags, Command Opcodes, Length Pointer        |
|                                                             |
|  [0x8100 - 0xFFFF] Shared DMA Buffer (Ring Buffer)          |
|      - Disk Read/Write Payload, Terminal I/O Buffer         |
+-------------------------------------------------------------+
              ^                                  ^
              | (Direct Memory View)             | (Direct Memory View)
              v                                  v
    +------------------+              +-------------------+
    | Wasm App (Logic) |              | JS カーネル (nuno)|
    +------------------+              +-------------------+

1. SharedArrayBuffer と Atomics によるアトミック同期
-----------------------------------------------------

WasmとJS間でのコンテキストスイッチ（関数呼び出し）コストを削減するため、
シグナリングにはメモリ上のフラグと Atomics.wait / Atomics.notify を利用します。

制御用レジスタ（Control Register）:

SharedArrayBuffer 上の特定領域に status_flag
（0: IDLE, 1: REQ_DISK_READ, 2: REQ_DISK_WRITE, 3: TERMINAL_OUT 等）を配置。

ノンブロッキング処理:

Wasm側が状態フラグを書き込み、Atomics.notify を発行。JSカーネル側のイベントループ
または Web Worker が変更を検知して非同期処理（IndexedDBアクセス等）を開始します。

2. リングバッファによる DMA (Direct Memory Access) 転送
----------------------------------------------------------

端末入力やIndexedDBのレコードアクセスといったデータ転送において、
引数経由で文字列や配列を受け渡すとコピーオーバーヘッドが発生します。

リングバッファ構造:

MMIO領域の後続に固定長の共有バッファ（例: 64KB）を確保。

ゼロコピーアクセス:

端末出力: WasmがDMA領域に文字データを直接書き込み、カーネル（JS）へポインタ長を通知
JS側は TextDecoder を使って Uint8Array ビューから直接VTERM/DOMへレンダリング。

レコード検索 (IndexedDB):

カーネル（JS）がIndexedDBから取得したレコード（Uint8Array）をDMA領域に直接 set() し
Wasm側に準備完了を通知。Wasmはメモリから直接デコード。

3. イベント駆動型Polling/Interrupt（割り込み模擬）
---------------------------------------------------

JSのシングルスレッド制約を回避するため、2つの運用形式が考えられます。

Wasm UI/Terminal: メインスレッド（DOM / WebGL描画用）

nuno Kernel (JS) + Storage: Web Worker

Worker側でIndexedDB制御とバックグラウンド処理を行い、MMIOメモリ経由で状態を同期します。

メモリマップド端末（MM-Terminal）の基本イメージ
================================================

画面テキスト/属性バッファ

例: 80x25 文字のテキスト VRAM（ASCII/UTF-8 用 2KB + 文字色・背景色等の属性用 2KB）
を Wasm メモリ上の固定アドレスに配置。

カーソル・制御レジスタ

cursor_x, cursor_y, render_dirty_flag などを配置。

描画（JS側）

JSカーネル側は requestAnimationFrame 内で render_dirty_flag を確認し、
フラグが立っていれば Canvas / OffscreenCanvas に対して VRAM の差分
（または一括）描画を行い、フラグを降ろす。

入力MMIOのメモリレイアウト設計
=================================

+------------------------------------------------------------------+
|               MMIO Input Registers (0x8000 - 0x800F)             |
+------------------------------------------------------------------+
| Offset | Field           | Type   | Description                  |
|--------|-----------------|--------|------------------------------|
| 0x00   | KBD_HEAD        | uint8  | キーリングバッファ Head 指針 |
| 0x01   | KBD_TAIL        | uint8  | キーリングバッファ Tail 指針 |
| 0x02   | MODIFIER_FLAGS  | uint8  | Shift, Ctrl, Alt, Meta 状態  |
| 0x03   | RESERVED        | uint8  | パディング                   |
| 0x04   | KBD_BUFFER[12]  | uint8  | 生スキャンコード/ASCIIリング |
+------------------------------------------------------------------+

Wasm（アプリ/シェル）側のポーリング読み出しメカニズム
------------------------------------------------------

Wasm側は関数呼出を受け取るのではなく、自身のメインループの周期（tick）で
HEAD と TAIL の差分をチェックするだけ

HEAD（0x8000）と TAIL（0x8001）を比較。

一致していなければ未処理の入力が存在するため、KBD_BUFFER[HEAD] から 1 バイト取得。

取得後、HEAD = (HEAD + 1) % 12 に更新して消費完了をカーネルに伝える。

テキストVRAM メモリマップ設計
===============================

画面サイズを一般的な標準ターミナルサイズである 80桁 × 25行（計2,000文字） と想定

+-----------------------------------------------------------------------------+
|                  VRAM / Display MMIO (0x8100 - 0x9083)                      |
+-----------------------------------------------------------------------------+
| Offset         | Field         | Type  | Size | Description                 |
|----------------|---------------|-------|------|-----------------------------|
| 0x8100         | CURSOR_X      | uint8 | 1    | カーソル X 位置 (0 - 79)    |
| 0x8101         | CURSOR_Y      | uint8 | 1    | カーソル Y 位置 (0 - 24)    |
| 0x8102         | CURSOR_STYLE  | uint8 | 1    | 0:非表示,1:点滅, 2:ベタ塗り |
| 0x8103         | RENDER_FLAGS  | uint8 | 1    | Bit0: DIRTY (画面更新フラグ)|
|----------------|---------------|-------|------|-----------------------------|
| 0x8104 - 0x88D3| TEXT_BUFFER   | uint8 | 2000 | ASCII/文字コードバッファ    |
| 0x88D4 - 0x90A3| ATTR_BUFFER   | uint8 | 2000 | 文字属性 (色・装飾)         |
+-----------------------------------------------------------------------------+
Total: 4,004 Bytes (~ 4 KB)

2. 1バイト属性（ATTR）のビットフィールド定義
--------------------------------------------

属性バッファの各1バイト（uint8）をビットマスクとして定義することで、
最小のメモリサイズで16色カラーと装飾表現に対応します。

Bit   Name        Description
0 - 3 FG_COLOR    前景色（16色 ANSIカラーコード: 0x0〜0xF）
4 - 6 BG_COLOR    背景色（8色 ANSI標準カラー: 0x0〜0x7）
7     ATTR_FLAGS  1: 下線（Underline）または反転表示
